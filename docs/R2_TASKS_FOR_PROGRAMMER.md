## 0. 这一轮要解决什么（先读这 6 行）

验收结论是「能跑起来，但还不能放心用」。R2 **不加新功能**，只做三件事：

1. **把不可信的结论变可信**：🟡 假黄 / 自相矛盾（D-03、D-04），限流导致的结论不可复现（D-05）。
2. **把"内部的东西"从用户眼前拿走**：i18n 键名、`slug:modrinth:` / `sha1:`、英文 argparse / JSON 异常（D-02、D-09、D-11、D-15）。
3. **把"报告就是交付物"这件事做完整**：日期列消失、下一步断号、重定向时假死（D-06、D-07、D-08）。

**R2 的完工判据不是"代码写完了"，而是"冻结修订上重跑验收，FAIL ≤ 5 且全部是 P3"**（见 §2）。

### R2-02 ｜ P0 ｜ 限速真正生效 + 结论可复现（**最高优先**）

- **来源**：D-05 / C17 / I1 / I2 / F3；根因与要求见 PRD §12.4。
- **现象**：200 模组冷跑 509 请求 / 76 秒 = **399 次/分钟 > 官方 300**；20 条因限流落 ⚪；冷跑 🔴57 与热跑 🔴69 不一致。
- **要做的事**：
  1. `RateLimiter` 改为**严格滑动窗口**：保留最近 60 秒的请求时间戳，窗口内已达 240 则 sleep 到最旧时间戳滑出；**令牌桶容量 = 1，初始为空**，禁止启动突发。
  2. 429：读 `Retry-After` / `X-Ratelimit-Reset` 全局暂停；重试耗尽**不立即落 ⚪**，而是进「待补跑队列」。
  3. **整轮末尾补跑**：所有模组跑完后，对待补跑队列做一轮**串行、≤ 60 次/分钟**的重试；仍失败才落 ⚪。
  4. 报告头：最终仍有因限流的 ⚪ 时，加一行 `⚠ 本次有 {n} 个模组因 Modrinth 限流未判定，建议稍后重跑（缓存已保存，重跑很快）`；结论行标注结论不完整。
  5. `--debug` 打印 `requests=N window_peak=M req/min`。
- **验收**：
  - 单测 `test_rate_limit.py::test_sliding_window`：假 clock 连发 500 次，断言**任意** 60 秒窗口 ≤ 240。
  - 单测 `test_rate_limit.py::test_bucket_starts_empty`：第一次 `acquire()` 后 1 秒内发起数 ≤ 5。
  - 真机：200 模组冷跑 → `--debug` 的 `window_peak` ≤ 240；⚪ **= 0**。
  - 真机：同一清单连跑两次，两份 `--json` 的 `{mod_status, reason}` 逐条 diff **为空**。
- **依赖**：无

## 5. 流程改进（写进团队约定，不是代码）

1. **每轮验收前打冻结 tag**（`git tag r2-accept-<n>`），验收期间 `src/` **只读**；任何结论必须写明 `git describe --tags --always` 的输出。
2. **禁止在验收窗口内改代码**。若必须热修，则作废本轮验收，改完重打 tag 重跑——**不允许"部分重跑"**（上一轮就是这样产生 16:50 与 17:00 两个不同结果的）。
3. 程序员每次提交前自跑 `pytest -m "not live"` + `test_output_purity`；**新增任何用户可见字符串都必须同时进 i18n 表**。
4. 交付说明必须包含：修订号、pytest 汇总、覆盖率数字与命令、200 模组冷跑/热跑的耗时与请求数与 ⚪ 数。
5. **不要为了通过验收而调参**：例如把默认 `--window` 降到 1~3 来压体积（PRD §11 Z11 已明令禁止）、或把限速调高来"跑得快一点"。
