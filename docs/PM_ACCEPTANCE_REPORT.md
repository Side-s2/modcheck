### D-01 ｜ **P1** ｜ `config set proxy null` 把代理设成字符串 `"null"`，静默废掉全部联网

- 复现：
  ~~~powershell
  & $py -m modcheck config set proxy http://127.0.0.1:9
  & $py -m modcheck config set proxy null      # 用户想"取消代理"
  & $py -m modcheck config show                # 显示「代理：null」——看起来像没设
  & $py -m modcheck scan mods_sample --profile x --yes
  ~~~
- 实际：`settings.json` 里写入 `"proxy": "null"`；此后**每一次网络请求都失败**，`scan` 打印
  `⚠ 连不上 Modrinth，本次只用 jar 内信息识别`，`check` 全部 ⚪。而 `config show` 显示 `代理：null`，用户会以为代理已清除。
- 期望：`config set proxy null`（或 `none`/`-`/`off`）应清空代理；`config show` 应显示「未设置」
- 影响：**所有联网用户**。这是"照着自己以为的语义操作一次，工具就永久性坏掉"的陷阱，且状态页在骗人。
- 现有绕法（未文档化）：`config set proxy ""`（空串）确实能清空；`none` / `-` 会写入同样的坏值。
- 建议：`config set` 对 `proxy` 做白名单解析（`null/none/-/""` → None；其余必须能 `urlsplit` 出 scheme+host，否则报错拒绝写入）；补一条单测。

### D-03 ｜ **P1** ｜ 🟡 组出现**自相矛盾**的行：同一个版本号既"不支持"又"可用"

- 复现：`& $py -m modcheck check --profile sample --mc 26.1 --loader fabric --no-color --quiet`
- 实际（逐字）：
  ~~~
  !  11 EntityCulling   entityculling  1.10.5 → 1.11.2   2026-09-21
        原因：Fabric 最新版 1.11.2 不支持 MC 26.1
        可用：1.11.2（2026-09-21）
  !  23 Syncmatica      syncmatica     0.3.18 → 0.3.20   2026-09-22
        原因：Fabric 最新版 0.3.20 不支持 MC 26.1
        可用：0.3.20（2026-08-20）
  ~~~
- 期望：用户能看懂"我到底该不该动它"
- 事实核查（我直接查了 Modrinth API）：EntityCulling 有 **6 条 version_number 都是 `1.11.2`、同一天发布**的记录，分别对应 26.3 / 26.2 / 26.1 / 1.21.8 / 1.21.5 / 1.21.4。程序按 BRIEF §7「用 latest_for_loader 判定」严格实现，逻辑没错；**错的是表达**——判 🟡「需要你拍板」，而实际上用户什么都不用做。

### D-04 ｜ **P1** ｜ "最新版"的版本号可能**比"可用"更旧**

- 复现：`& $py -m modcheck check --profile sample --mc 26.3 --loader fabric --no-color --quiet`
- 实际：
  ~~~
  !   5 Carpet Org Addition   carpet-org-addition   1.45.1 → 1.41.7 (v1.41.7+2609272022)  2026-09-27
        原因：Fabric 最新版 1.41.7 不支持 MC 26.3
        可用：1.46.0（2026-09-16）
  ~~~
- 事实核查：`1.41.7`（2026-09-27，只标 1.21.x）确实比 `1.46.0`（2026-09-16）**发布更晚**，所以按"发布时间最新"它确实是"最新版"；但屏幕上 1.41.7 与 1.46.0 并列时，用户只会得出"这个工具在胡说"。
- 期望：不要用"最新版"这个绝对词去指一个版本号更小的条目。
- 建议：版本列语义化（如「该加载器最近发布」），或在"可用"版本号更大时附加一行说明。

### D-05 ｜ **P1** ｜ 200 模组冷启动**触发 Modrinth 限流**，且两次运行结论不一致（C17 失败）

- 复现（200 个真实 Modrinth slug 的清单，先清空缓存）：冷跑一次、紧接着再跑一次。
- 实际：

  | | 用时 | 请求 | 🟢 | 🟡 | 🔴 | ⚪ |
  |---|---:|---:|---:|---:|---:|---:|
  | 冷缓存 | 76 s | **509 次** | 96 | 27 | **57** | **20** |
  | 热缓存 | 6 s | 38 次（353 命中） | 101 | 30 | **69** | **0** |

  20 条 ⚪ 的原因全部是 `原因：被 Modrinth 限流（请求太频繁），已自动重试仍失败`。
- 期望：① 遵守 BRIEF §12「Modrinth 官方限速 300 req/min，程序必须遵守」；② 同一清单+同一目标，两次运行结论一致（清单 C17）
- 实测速率：509 / 76.5 s = **6.65 req/s ≈ 399 次/分钟 > 300**，超限 33%。**配置页那句「并发数：6（上限 8，Modrinth 限速 300 次/分钟）」目前是假的。**
- 影响：**所有 100+ 模组的用户**。第一次运行得到 10% 未判定 + 偏乐观的阻塞数（57 vs 实际 69），用户按 57 去处理，升级时会踩到剩下 12 个。
- 建议：http 层加**全局令牌桶（240 次/分钟，留 20% 余量）**，而不是只靠并发数；被限流的条目在报告头汇总提示"本次有 N 个因限流未判定，建议稍后重跑"；或对限流项自动做一轮串行慢速重试后再落报告。

### D-08 ｜ **P1** ｜ 输出被重定向时会弹出交互并**把提示写进文件**、看起来像卡死；EOF 后内部错误串被当成"原因"

- 复现（真实终端里，标准输出重定向；清单里有匹配不上的条目）：

## 5. 如果只能改 3 件事

**第一件：把"我不确定的东西"变成"确定"——修 D-03 / D-04 的 🟡 自相矛盾与假黄（判定层 + 文案层）**
理由：这是**用户信任的唯一来源**。26.1 那一次运行 30 个模组里 24 个 🟡，其中至少 2 行左右互搏、1 行"最新版"版本号比"可用"还小。服主看完第一份报告就会得出"这工具不准"，后面所有正确的结论都救不回来。这一条不修，工具等于没做。

**第二件：修 D-01（`config set proxy null` 废掉联网）+ D-02（i18n 键泄漏）**
理由：这两条是"**踩一次就永久坏 / 永远看不懂**"的类型。D-01 让工具彻底不可用、且状态页在骗人；D-02 让用户在配置目录只读或 Mojang 抖动时看到 `«warn.xxx»`。改动都不大，但决定"这软件像不像个成品"。

**第三件：修 D-05（限速）+ D-07 / D-06（报告的日期列与断号）**
理由：D-05 是**设计目标规模（200 模组）下的正确性问题**——首次运行 10% 未判定、两次运行结论不同（57 vs 69 个阻塞），用户会按错的数字去处理。D-07 / D-06 是"报告就是最终交付物"的完整性问题：一列关键信息消失、步骤编号断号，都会被当成 bug 而不是"设计"。

> 若还有第 4 件：D-08（重定向时弹交互、看起来卡死、内部错误串进报告）。它同时命中"看起来很卡"和"报告里有程序内部出错"两种最伤观感的症状。

## 6. 总评：现在能不能交给一个真实服主用？

**结论：能"用起来"，但还不能"放心用"。建议再走一轮迭代（R2）后再交付。**

支持"能用"的证据（都是真机、真数据）：

- 导出 `--json/--md/--csv` 质量高（JSON 有 schema_version + status + reason_key；MD 可直接贴群；CSV 带 BOM，Excel 不乱码）。

不能直接交付的核心理由（按严重度）：
1. **信任风险**：🟡 组自相矛盾 / 假黄（D-03、D-04）——用户会认为工具不准。
