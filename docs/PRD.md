## 1. 产品定位与成功标准

### 1.1 一句话定位

**给 Minecraft Java 版服务端服主用的命令行工具：升级游戏版本之前，一条命令查清自己服务器上的模组是否都已经支持目标版本，并把结论分成「就绪 / 需降级 / 阻塞 / 未判定」四类，每条都给出下一步该做什么。**

### 1.2 反向定位（同样重要）

它**不是**模组管理器，**不是**下载器，**不是**依赖分析器。它只做一件事：**在你动手升级之前，把风险摊开给你看**。任何"顺手帮你把模组装好"的念头都是范围蔓延。

### 1.3 成功标准（可量化，验收时逐条量）

| 编号 | 判据 | 阈值 |
|---|---|---|
| S1 | **首次检查**（无缓存）200 个模组的耗时 | **≤ 90 秒**（实测外推 30~60 秒，留 50% 余量） |
| S2 | **二次检查**（缓存命中，TTL 6 小时）200 个模组的耗时 | **≤ 5 秒** |
| S3 | **误报为绿的比例**（把不兼容说成 🟢 就绪） | **0**。任何一条误报都是 P0 缺陷 |
| S4 | 单个模组失败导致整体检查失败 | 0 次，100% 降级为 ⚪ 未判定 |
| S5 | 程序输出中出现的 Python traceback 次数 | 0（含断网、限流、磁盘满、jar 损坏、中文编码、Ctrl+C） |
| S6 | 200 个模组、其中 1 个超时 | 退出码 2，其余 199 个结论完整正确 |
| S7 | 20+ 条核心错误文案 | 服主读完知道"下一步做什么"（人工评审，见验收清单 D 组） |
| S8 | `--no-color` 与管道重定向下 | 100% 可读，无 ANSI 转义残留 |
| S9 | 冷启动到主菜单 | ≤ 2 秒（**启动时绝不联网**） |
| S10 | 未判定项可见度 | 不折叠、不只出现在统计里，必须有独立分组 |
| S11 | 30~90 秒的等待期 | 进度条**每秒至少刷新一次**，且显示"当前在查哪个模组"（见 §5.5） |
| S12 | 中断响应 | 按 Ctrl+C 后 **≤ 1 秒**开始输出已完成部分的摘要 |
| S13 | 单模组网络成本 | ≤ 3 个请求、≤ 5 KB（基准：≤ 2 个请求、≈ 2.2 KB） |
| S14 | 缓存体积 | 精简后不超过原始响应的 15%（基线实测 10%） |
| S15 | 分发形态（主 Agent 真机实测） | 默认交付 Nuitka **standalone** 目录（启动 < 1 秒）；`--onefile` 单文件为**可选**产物，**首次启动约 7 秒**（解包），必须在 README 里写明；两种产物中文输出均**不得乱码** |

**明确不写的措辞**：不承诺"实时""秒级""瞬间"。二次检查写"几秒内"，首次写"通常 30~90 秒"。

### 1.4 反例驱动：什么情况下这个功能会害了用户

1. **误报为绿**（最严重）：服主看到"🟢 就绪"直接升级，服务器启动崩溃，玩家进不来，半夜被骂。——所以：不知道的一律 ⚪，绝不猜。
2. **误报为红/黄**：服主白忙一晚上去换模组，结果本来能用。——所以：判定必须按目标加载器过滤（见 §1.5）。
3. **假装查完了**：网络断了但输出"全部就绪"。——所以：数据源不可用必须退出码 4 且结论写"无法得出结论"。
4. **静默丢数据**：同一模组有两个 jar，程序只报一个，服主没发现，服务器照样崩。——所以：必须显式告警并列出两个文件名。
5. **结论不完整却像完整**：中断/超时/限流之后报告看起来和完整报告一样。——所以：不完整的报告必须在**结论行**上标记"结论可能不完整"。
6. **靠文件名猜出来的模组被当成事实**：文件名解析实测 14 个里只对 3 个。——所以：猜测结果必须带 ⚠ 可见标记 + `match_status="guess"`，绝不静默。

### 1.5 误报风险专章（**基线 v1.1 实测教训**）

**案例：JourneyMap 被误判为"需降级"。**

Modrinth 上 JourneyMap 为同一个版本号发布了 4 条记录，发布时间**完全相同**（2026-09-19）：
`26.3-6.0.9+paper` / `26.3-6.0.9+neoforge` / `26.3-6.0.9+forge` / `26.3-6.0.9+fabric`。

- 如果程序按"全局最新"判定：很可能取到 `+paper` 那条 → 它不含 fabric → 得出"没有 fabric 的最新版" → **🟡 需降级（误报）**，服主会去折腾一个根本不需要折腾的模组。
- 正确做法（基线 §7）：**判定一律以 `latest_for_loader(M,L)` 为准**——先按目标加载器过滤，再看发布时间最新的一条。这样 JourneyMap 在 26.3/fabric 下正确得到 🟢。
- 同类风险还有两个：① `date_published` 会并列，**禁止自行重排序**（基线 §7 明确要求信任 API 返回顺序）；② 请求必须带 `loaders=["fabric"]` 过滤，而不是拉回来本地挑。

**产品层的连带要求**：
- 用户可见文案里**不许出现光秃秃的"最新版"**，一律写「Fabric 最新版」「NeoForge 最新版」（决策 D16）。
- 报告里"最新版本号"后面要能看出它是哪个加载器的（本报告的目标加载器只有一种，写在报告头，因此行内不重复）。
- **回归用例**（进验收清单 C 组）：目标 `26.3 / fabric` 下 JourneyMap 必须显示 🟢 就绪。

## 2. 用户画像与场景故事

### 2.1 用户画像

**主画像「老王」**：32 岁，和朋友开了一个 20 人的生存服，服龄 3 年。会改 `server.properties`、会看日志前 30 行、知道 Fabric 和 Forge 的区别，但不想读英文 API 文档。服务器有 120 个模组，三年里陆续加的。原话：**"我不是不会查，我是要一个个去搜 120 遍，一晚上就没了。"**

**次画像「小陈」**：大学生，帮社团开服，20 个模组，爱用最新版，经常遇到"这个模组还没跟上"。

**共同特征**：出问题没人可问；极其厌恶看不懂的报错和"假装成功的工具"；中文界面是刚需。

### 2.2 场景 A：升级前夜（主场景，正常路径）

- **21:40** MC 26.3 发布第 4 天。老王决定今晚试试。
- **21:41** 输入 `modcheck`。主菜单第一行显示配置目录，第二行显示「Modrinth 已启用 ｜ CurseForge 未启用（缺少 API Key）」——他知道自己主要用 Modrinth，不慌。选 `[1]`。
- **21:42** 选清单「服务器A（120 个模组）」→ 版本列表第一个就是 `26.3（最新正式版）` → 加载器 `Fabric`（默认，回车）。
- **21:42** 确认页写着"预计请求约 240 次"，他确认。进度条开始走：
  `正在检查 120 个模组……  [########------------]  42/120  当前：JourneyMap  已用 12 秒`
  到 60/120 时，行尾多了一句 `已发现 2 个阻塞`——他提前就知道今晚有事要干。
- **21:43** 报告出来（用时 41 秒）。**第一屏就是 🔴 阻塞（3 个）**：Create（原来是 Forge 的）、Create Fabric（最高只到 1.20.1）、Thermal Series（Modrinth 上找不到，行尾标着 `~` 说明这是靠文件名猜的）。
- **21:44** 🟡 需降级 2 个，其中 JEI 写着"只有测试版支持"，FerriteCore 写着"你本地就是这个版本，无需改动"。⚪ 未判定 2 个明确写着"不算失败"，并给了一行可直接复制的重跑命令。
- **21:46** 他复制命令行重跑，因为缓存命中，**4 秒**就出了结果，⚪ 变成 0 个。剩下 3 个红色他自己处理。
- **22:05** 再次检查 →「✅ 可以升级」，退出码 0。升级成功。
- **总耗时约 24 分钟**（其中 18 分钟是他自己做决策，工具累计只花了 1 分多钟）。对比手工：**3 小时以上**。

### 2.3 场景 B：换加载器（Fabric → NeoForge）

老王想换成 NeoForge（某个模组只有 NeoForge 版）。`modcheck check --profile 服务器A --mc 26.3 --loader neoforge` 之后，🔴 阻塞项里一半是"该模组没有 NeoForge 版本（仅有 Fabric）"。**换加载器的代价一目了然**，他最后没换。

### 2.4 场景 C：失败路径（四种真实翻车方式）

**C1｜模组不在 Modrinth 上。** Thermal Series 只在 CurseForge 发布。程序搜不到 → 不崩、不乱报，🔴 `NOT_FOUND`，文案写明"若只在 CurseForge 上，本工具暂不支持（CurseForge 数据源未启用）"。

**C2｜网络抽风。** 查到第 87 个时 WiFi 断了。剩余模组全部 ⚪，报告完整输出，结论行写着"另有 N 个未判定，结论可能不完整"，退出码 2，末尾给出代理设置命令。恢复网络后 `--refresh` 重跑，缓存命中只花了 12 秒。

**C3｜最危险的一种：误报为绿。** 假设程序在搜不到项目时"聪明地"用了模糊匹配，把 `Carpet TIS Addition` 匹配到 `Carpet` 并标成 🟢。老王升级，服务器启动直接崩，日志里是 `NoClassDefFoundError`，他根本不知道是哪个模组，只能人肉二分法排查——**这就是本工具必须"绝不猜"的全部理由**。

**C4｜只有一份文件名清单。** 老王的朋友在群里发了一张 80 行的文件名截图，他照着敲成一个文本文件，没有 jar。他运行 `modcheck scan --from-list 文件名清单.txt --profile 服务器A`，程序只能靠文件名猜：
- 80 个里 61 个猜出了一个 modid，其中 43 个在 Modrinth 上找到了完全同名的项目；
- 报告顶部写明 `识别来源：Modrinth 文件指纹 0 ｜ jar 内信息 0 ｜ 文件名猜测 80`；
- 43 个有结论的行，modid 前面都带 `~`，报告里有专门一段说明"带 ~ 的条目是从文件名猜的，不一定准确，请人工核对"；
- 剩下 37 个标 ⚪ 未判定，末尾提示"补上 jar 文件可以精确识别"。
**老王知道这份报告只有一半可信——这正是我们要的效果，而不是假装全都知道。**

### 2.5 等待体验（30~90 秒的等待是产品的一部分）

首次检查 200 个模组要等 30~90 秒。这段时间用户看到什么，直接决定他觉得这工具"快"还是"卡死"：

| 时刻 | 用户看到 | 设计理由 |
|---|---|---|
| 0 秒 | 进度条 + 总模组数 + 已用时间 | 让他知道开始了 |
| 每个模组完成 | 进度条前移 + **当前模组名** | "正在查 JourneyMap" 比一个数字更有说服力 |
| 首次发现阻塞项 | 行尾出现 `已发现 1 个阻塞` 并累加 | 提前给结论，等待变得有价值 |
| ≥ 20 个之后 | 行尾出现 `预计还需约 24 秒` | 有 ETA 才敢去泡面；估算不稳时宁可不显示 |
| 随时 | Ctrl+C → 1 秒内输出已完成部分的摘要 | 不惩罚用户的选择 |
| 缓存命中时 | 报告头 `请求 26 次（缓存命中 114 次）` | 让"第二次只要 4 秒"这件事可解释，不是玄学 |

## 4. 端到端流程

### 4.1 路径一：交互式菜单（老王的主路径）

```

  → 冷启动自检：终端编码处理 → 配置目录探测/创建 → 读 settings.json → 可写性探测 → 颜色能力探测
  → 打印启动横幅（版本 + 配置目录 + 数据源状态）
  → 读 profiles/
      ├─ 有清单 → 主菜单
      └─ 无清单 → 主菜单 + 顶部提示"先选 [2] 扫描 mods 文件夹"
  → 选 [1] 检查模组兼容性
      → 无清单？ → 提示 + "现在扫描？(Y/n)" → Y 进入 [2]
      → 选清单（编号 / 输入路径 / b 返回）
      → 拉官方版本清单（失败 → 允许手动输入，并提示"未取到官方列表"）
      → 选目标 MC 版本（最近 10 个正式版编号 / m 手动 / b 返回）
      → 校验格式与存在性 → 不合法就地提示重选，不退出
      → 选加载器（1 Fabric / 2 NeoForge / 3 Forge / d 默认 / b 返回）
      → 确认页（清单 / 模组数 / 目标版本 / 加载器 / 数据源 / 预计请求数）→ (Y/n)
      → 开始检查
          → 进度行每秒刷新（含当前模组名、已发现阻塞数）
          → 未找到完全同名 → 暂停进度 → ⚠️ 告警 + 候选 + 交互选择
              ├─ 1..5 选定 → 写回清单（manual）→ 继续
              ├─ m 手动输 slug/URL → 校验存在 → 写回 → 继续
              ├─ s 本次跳过 → ⚪ UNMATCHED → 继续
              ├─ i 永久忽略 → ⚫ IGNORED 并写回 → 继续
```

### 4.3 判定算法（**基线 §9.5 的 limit 过滤法，程序必须照此实现**）

> 为什么不能用全量拉取：实测 JEI 单个模组就有 3736 条版本 / 6.8 MB；200 个模组外推约 326 MB，完全不可行。用 `limit` + 过滤后，每个模组只需 2（最多 3）个请求、约 2~5 KB。

**请求定义**（`WINDOW = 25`，可用 `--window` 覆盖；`L` = 目标加载器，`V` = 目标 MC 版本）：

| 代号 | 请求 | 用途 |
|---|---|---|
| A | `GET /project/{slug}/version?loaders=["L"]&version_type=release&limit=WINDOW` | 目标加载器的**最新正式版** |
| B | `GET /project/{slug}/version?game_versions=["V"]&loaders=["L"]&version_type=release&limit=WINDOW` | 目标加载器 + 目标 MC 的**最新兼容正式版** |
| B2 | `GET /project/{slug}/version?game_versions=["V"]&loaders=["L"]&limit=WINDOW` | 仅在 B 为空时发起：放宽到 beta/alpha |
| A2 | `GET /project/{slug}/version?loaders=["L"]&limit=WINDOW` | 仅在 A 为空时发起：判断是"完全没有该加载器"还是"只有测试版" |

`--pre` 时：**A、B 都去掉 `version_type=release` 过滤**（等价于直接使用 A2/B2），且不再产生 `PRERELEASE_ONLY`。

**判定（按顺序，第一个命中即返回）**：

```
① A 为空 且 A2 为空            → 🔴 NO_LOADER      （附：该项目实际有哪些加载器）
② A 为空 但 A2 非空            → 继续走 ④⑤（说明该加载器只有 beta/alpha）
③ B 非空 且 B[0].id == A[0].id → 🟢 OK              （目标加载器的最新正式版就支持 V）
④ B 非空                       → 🟡 OLD_VERSION_ONLY（可用 latest_compat = B[0]）
⑤ B 为空 且 B2 非空            → 🟡 PRERELEASE_ONLY （可用 latest_any = B2[0]）
⑥ 其余                         → 🔴 NO_MC_VERSION   （max_supported_mc 由 A 窗口内所有 game_versions 的最高正式版得出）
项目不存在（404）              → 🔴 NOT_FOUND
项目存在但一个文件都没有        → 🔴 NO_FILES（独立码，不复用 NO_LOADER）
provider 抛其它 ProviderError  → ⚪ UNKNOWN(ERROR)
非交互模式未能精确同名匹配      → ⚪ UNKNOWN(UNMATCHED)
match_status == "ignored"      → ⚫ IGNORED（不参与统计）
```

**必须注意的五点**：

1. **绝不允许自行重排序**。基线实测 `/project/{id}/version` 已按发布时间**倒序**返回；`date_published` 会并列，自己排序会引入不稳定。直接取数组第一个。
2. **绝不允许用 `/project/{id}` 返回的 `versions[]` 判断最新版**——实测 carpet 的前 6 条是 2022 年的。该字段只能用来判断"这个项目有没有版本"。
3. **判定必须以 `latest_for_loader` 为准**（§1.5 的 JourneyMap 案例）。
4. **⑥ 的 `max_supported_mc` 是从 A 窗口内推算的近似值**，文案里写"最高支持到 MC 26.1"，不要写"绝对不会支持 26.3"。
5. **限流/超时/5xx 一律 ⚪**，绝不落入 🔴（这是 §1.4 的第 1 条红线）。

**算法正确性**：基线已用该算法对 carpet / journeymap / jei 在 26.1 与 26.3 下逐条与全量法比对，**5/5 一致**；这 5 条必须原样进单测（验收清单 C 组）。

### 4.4 模组识别流程（基线 §11.3）

```
① 读 jar 内部元数据（fabric.mod.json → quilt.mod.json → neoforge.mods.toml → mods.toml → MANIFEST.MF）
      → modid / 展示名 / 模组版本                                    【高置信】
② 算 jar 的 sha1 → 批量 POST /v2/version_files 反查
      → project_id + 用户当前安装的确切版本号                        【高置信】
③ 用 ① 或 ② 得到的名字做精确同名搜索（§8 规则，slug 优先）           【高置信】
④ 都不行 → 文件名尽力解析 → match_status="guess"，报告里标 ~       【低置信，UI 必须提示】
⑤ 仍不行 → ⚠️ 告警 + 交互选择（非交互模式标 ⚪ UNMATCHED）
```

**硬性断言（基线 §11.2）**：
- ❌ 绝不用文件名推断出的 MC 版本作为判定依据；
- ❌ 绝不用文件名推断出的名字搜到结果后"就近取一个"；
- ✅ 文件名解析的**唯一合法用途**是没有 jar 时的最后兜底，且必须标 `guess`。

### 5.5 进度显示（逐字，**重点**）

进度行**每秒至少刷新一次**（即使用户在等一个慢请求），格式按终端宽度分级拼装：

| 宽度 | 输出 |
|---|---|
| ≥ 110 | `正在检查 {total} 个模组……  [{bar}]  {done}/{total}  当前：{name}  已发现 {b} 个阻塞  已用 {s} 秒  预计还需约 {eta} 秒` |
| ≥ 100 | `正在检查 {total} 个模组……  [{bar}]  {done}/{total}  当前：{name}  已用 {s} 秒` |
| ≥ 80 | `正在检查 {total} 个模组……  [{bar}]  {done}/{total}  已用 {s} 秒` |
| < 80 | `检查中 {done}/{total}` |

样例（宽度 110）：
```

```

**规则**：
- `{bar}` = 20 格，已完成 `#`、未完成 `-`；模组数 < 3 时**不显示进度条**（改为一行 `正在检查…`）。
- `{name}` 取当前正在请求的模组显示名，超过 20 显示列截断加 `…`。
- `{b}` 只在**已确认**的 🔴 数量 > 0 时出现（不提前把 ⚪ 算进去）。
- `{eta}` 只在 `done ≥ 20` 且最近 20 个的平均耗时能给出稳定估算（波动 < 50%）时出现；否则不显示。
- 非 TTY（重定向/管道）：不打进度行，改为每完成 20% 打印一行 `已检查 {done}/{total}……`。
- `--quiet`：完全不显示进度。
- 检查结束：进度行**清空**，不残留在报告上方。
- 中断：清空进度行 → 打印 `已中断（按了 Ctrl+C）。本次检查了 {done}/{total} 个模组，结果不完整，只列已查出的问题项：` → 简版清单。
- 交互式匹配弹出时：先清空进度行，交互结束后重画。

### 5.11 `--quiet` 的准确行为（主 Agent 批复补充）

`--quiet` **只做两件事**，其余一律不变：

1. 不显示进度条（改成静默）；
2. 🟢 就绪组只打印一行 `（{n} 个，已省略明细）`，不逐条列出。

**必须仍然完整输出的内容（不得因 `--quiet` 省略）**：

- 🔴 阻塞组：逐条完整输出（主体行 + 原因 + 建议）；
- 🟡 需降级组：逐条完整输出（主体行 + 原因 + 可用 + 建议）；
- ⚪ 未判定组、⚫ 已忽略组：完整输出；
- 报告头、汇总行、结论行、识别来源行、说明段、下一步清单：**全部保留**；
- `--json` / `--md` / `--csv` 导出的内容**完全不受 `--quiet` 影响**（导出永远是完整的）。

> 理由：`--quiet` 是给"我就想看问题"的用户用的，不是给"我要一份残缺报告"的用户用的。

## 6. 分组与排序决策

### 6.1 决策：**问题优先，就绪最后**

固定顺序：**🔴 阻塞 → 🟡 需降级 → ⚪ 未判定 → 🟢 就绪 → ⚫ 已忽略**。

### 6.2 面向服主的理由

1. **服主打开报告只问一个问题：「我今晚能不能升级？」** 能阻止他的只有 🔴，所以 🔴 必须在第一屏，不用滚动、不用搜索。
2. **🟡 是"需要拍板"而不是"需要修"**，紧跟 🔴：刚看完"哪些必死"，接着看"哪些要权衡"。
3. **⚪ 放在 🟢 之前是刻意的**：⚪ 意味着"还不知道"。如果放最后，服主看完一大片 🟢 很容易直接关窗口，把未知当成没问题——这正是我们要避免的误判。放在 🟢 前面，他必须"跨过"未判定项才能看到好消息。
4. **🟢 放最后**：它是数量最多的一组（200 个里可能有 190 个），放前面会把真正的问题挤出屏幕。就绪组是"确认信息"，不是"待办信息"。
5. **⚫ 已忽略永远最后**且不进总数，避免污染"成功率"的感觉。

### 6.3 组内排序

| 组 | 排序规则 |
|---|---|
| 🔴 / 🟡 / ⚪ | 按清单里的原始顺序（稳定、可预期，便于两次运行对比），不按名称排序 |
| 🟢 | 按清单原始顺序，便于与 mods 文件夹对照 |
| ⚫ | 名称升序 |

**稳定性要求**：同一清单 + 同一目标版本，两次运行的组内顺序必须完全一致；数据源返回顺序不得影响报告的组内顺序（判定只取 `A[0]` / `B[0]` 的**值**，不用其顺序做展示排序）。

## 8. 范围边界（本期明确不做）

1. ❌ **不做 CurseForge 实现**（只留 Provider 空位 + 文档）。界面显示"未启用（缺少 API Key）"，不报错、不计入红色。
2. ❌ **不做全量版本拉取**（基线 v1.2 实测：单模组可达 3736 条 / 6.8 MB）。一律用 `limit` + 服务端过滤。
3. ❌ **不做下载 / 替换 / 安装模组**，不写用户的 mods 文件夹（只读）。
4. ❌ **不做 GUI**（但 core 必须能被 GUI 直接调用：无 print、无 input、无 sys.exit）。
5. ❌ **不做依赖递归解析**（只对 `fabric.mod.json` 的 depends 做一层提示，不影响三态判定）。
6. ❌ **不做 MC 版本宽松/模糊匹配**（决策 D9）。
7. ❌ **不做快照版本检查**（不解析 `24w14a`/`26.3-snapshot-2` 的可用性）。
8. ❌ **不用文件名解析结果做任何判定**（基线 §11.2 硬性要求）。
9. ❌ **不做多语言**（仅 zh_CN；文案集中在 `i18n.py`）。
10. ❌ **不做模组包（.mrpack / .zip）解析**。
11. ❌ **不做自动更新 / 定时监控 / 后台常驻**。
12. ❌ **不做 Web / 服务端 / 多用户**。
13. ❌ **不引入任何第三方运行时依赖**（含 rich / click / requests / colorama / wcwidth）。
14. ❌ **不做 Modrinth 登录 / OAuth / 私有项目**。
15. ❌ **不做"智能推荐替代模组"**（容易推荐错，宁可不做）。
16. ❌ **不把 onefile 当默认分发形态**（主 Agent 实测：首次启动约 7 秒；默认 standalone）。
